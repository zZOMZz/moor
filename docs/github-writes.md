# GitHub 审阅与代码发布

Moor 的“审查、评论与代码发布”面板支持查看 PR 文件 diff 和行评论、发布评论、创建或修改 PR、合并 PR，以及在执行电脑提交选中文件、推送明确的分支。每次写入都先保存草稿、读取当前状态，再展示具体操作，由用户点击最终确认；浏览、刷新、重连和恢复主机不会发布内容或启动 Agent。

本页描述 M4.4 的实现边界。合成测试使用临时 Git 仓库、裸仓库接收端和虚构的 GitHub HTTP 响应；本批浏览器与最终检查状态见[功能计划](roadmap.md)和[设备验收](validation.md)。真实 GitHub 账号、组织策略、Mac 安装包及 iPhone/PWA 尚未完成专项验收。

## 开启外部写入

先在执行电脑按[GitHub 配置步骤](github.md#在执行电脑配置)登记并验证项目仓库。每个项目的外部写入默认关闭，需在 **Moor → 连接设置 → GitHub** 明确开启。这个开关不授予 GitHub 权限；仍需为该仓库配置实际可用的 token。手机和远端 Web 没有修改 token 或开启主机写入的接口。

本机 CLI 可通过原 stdin 配置入口提交 `project-writes`，字段为 `expectedRevision`、`localProjectId` 和 `enabled`。开启前项目必须已验证；重新绑定仓库会恢复为关闭状态。关闭、替换凭据或改变项目配置会使旧页面的授权版本失效，新操作必须重新读取。已知结果的历史确认仍沿用原操作编号。

| 操作                        | GitHub 细粒度仓库权限                     |
| --------------------------- | ----------------------------------------- |
| Issue/PR 会话评论           | Issues 写，或 Pull requests 写            |
| PR 行评论、回复、创建和编辑 | Pull requests 写                          |
| 合并 PR、推送代码           | Contents 写；相关预检视图还需对应读取权限 |

权限、组织审批与分支保护由 GitHub 决定，Moor 不寻找其他凭据绕过限制。各接口权限见[会话评论](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment)、[审阅评论](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request)和[合并 PR](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)。

**本地提交不需要 GitHub 配置、token 或外部写入开关。** 执行电脑仍须在线，当前目录和会话状态须允许提交。

## 审阅、草稿与最终确认

从 GitHub 条目或 Git 工作目录进入发布面板，手动读取当前能力和目标。PR 分别展示 head 与 base 的仓库、分支和完整 SHA；来自 fork 的 PR 保留两侧身份。浏览器只在内存中保留远端读取结果，离线或目标、授权变化后清除这些结果。

PR 文件按页读取。可以查看原路径与新路径、补丁和行号；只有完整且可验证的补丁行才允许创建行评论。没有补丁或补丁截断时，页面不会推断二进制内容或制造可评论的行号。行评论同步也是手动分页读取，保留当前和原始提交、行号及回复关系；旧评论不会自动挪到新行。回复针对顶层审阅评论，GitHub 不支持向回复再次创建回复，见[审阅回复接口](https://docs.github.com/en/rest/pulls/comments#create-a-reply-for-a-review-comment).

草稿保存手工输入和明确选择的目标。主动选择“使用当前 PR 内容创建编辑草稿”会复制所见内容，之后按普通草稿保存；正文被截断或超过 12,000 字符时不开放该入口，以免用未完整读取的文本覆盖原文。撤销 GitHub 授权不会删除这份用户主动保存的文本。最终确认前重新读取条目版本、PR 提交和评论定位；状态已改变时保留草稿，要求重新审查，不自动改投其他仓库或行。

最终确认展示正文、PR 编号、评论路径与行号、分支、SHA、合并方式，或本地提交的文件、作者和说明。确认前尚未发出写入。浏览器先以完整账号、设备、执行工作区、项目和会话为键保存原请求；不同页面竞争保存时采用版本比较，保存失败或冲突即停止发布。

## 提交选中文件

本地提交针对当前会话实际使用的原目录或 Moor worktree。选择文件后查看相对 HEAD 的内容，再填写作者姓名、邮箱和提交说明。提交使用所选文件的完整字节和执行权限；文本预览截断时会明确提示，二进制文件显示类型与大小。

主机将父提交、分支、索引摘要、选中文件版本、作者、首次计划生成时的时间以及最终提交对象保存为原操作计划。真正构造 blob 的那次读取也必须匹配已审查的字节和权限。确认期间文件、HEAD、暂存区或目录身份变化都会阻止继续；恢复不会换一批文件、更新时间或生成第二个提交。

未选择文件的暂存内容和工作目录内容保留原样。提交不运行仓库 hooks、filters、签名程序或凭据助手；执行型配置、子模块、稀疏检出、冲突、隐藏索引状态和不支持的仓库布局会被拒绝。当前最多选择 50 个文件，每个文件最多 1 MiB，选中文件合计最多 8 MiB。项目子目录只允许选择该项目内的相对路径。

主机保护同一仓库目录中的活动会话、Fork、worktree 清理及其他写入；存在未确认的本地提交时不能开始新的 Agent 回合。分支更新和索引落盘是两个步骤，故断线后必须核实两者，不能仅凭看见一个提交就宣称操作完整结束。目录与备份规则见[Git 与会话工作目录](git-workspaces.md)。

## 推送与 PR 操作的范围

推送目标固定为本机已授权的 GitHub.com 仓库及当前同名分支。确认页展示本地 HEAD 和预期远端 OID；推送前重新读取远端，已有远端提交必须是本地 HEAD 的祖先。发送包含预期旧 OID，远端在此期间前进会产生冲突。Moor 不强制推送，不删除远端分支，不读取 Git remote 来改写目标，也不调用仓库配置的 transport 或 credential helper。推送成功不代表 CI 已完成。

创建 PR 当前选择已授权仓库内的真实 head/base 分支，创建为普通或 Draft PR；可编辑已有 PR 标题与正文、关闭或重开，以及选择 merge、squash 或 rebase。Moor 会在发出请求前核对条目版本和已选择的提交。

**创建、编辑和改变 PR 状态没有原子的版本条件。** GitHub 的这些 POST/PATCH 接口不支持把 Moor 的预期版本作为服务端比较条件；预检之后仍可能出现并发编辑或分支变化。若创建返回的实际 head SHA 已改变，主机保留已创建 PR 的结果并提示实际提交，不把已经创建误报成未执行。合并接口则传递准确 head SHA，GitHub 在不匹配时拒绝。详见[创建、修改与合并 PR](https://docs.github.com/en/rest/pulls/pulls)及 GitHub 对[非安全 HTTP 方法的条件请求限制](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests-if-appropriate)。

本批不提供自动提交、自动推送、强制覆盖、自动合并、review 审批意见提交、标签/受让人编辑、工作流重跑、拉取远端代码或任意 Git/HTTP 命令。GitHub Enterprise 的自定义域名仍是后续范围。

## 结果未知、核查与结束

| 显示结果               | 含义与下一步                                                   |
| ---------------------- | -------------------------------------------------------------- |
| 主机已确认             | 返回匹配原请求的评论/PR 身份或提交 SHA；无需再次发布           |
| 主机拒绝或确认未执行   | 原请求已结束；需要修改后重新审查，或明确创建另一操作           |
| 结果未知               | 请求可能已发出；保留原编号和原参数，手动核查                   |
| 已结束核查，结果仍未知 | 仅解除本机等待，不表示远端操作已取消；不要据此重新发布同一内容 |

“核查原操作结果”只读原计划对应的结果。它既不会重发写入，也不会首次执行一个尚未到达主机的操作。没有找到结果、只读到一页、权限失效或查询失败，都不能证明操作未执行。对于评论与 PR 创建，主机在正文末尾附加不可见的 Moor 操作标记；核查同时比较完整正文摘要、账号数字 ID 和目标定位。标记不是 GitHub 的幂等键，也不是新的访问凭据；Moor 显示正文时移除该精确尾标记。

收到远端结果后，主机优先保存最小已知身份；之后的授权或网络失败不会导致再发一次写入。若响应完全丢失，用户可以手动查看其他核查页；找不到仍保持未知。刷新和重连只恢复本机草稿与原请求。

“结束原操作核查”有两种结果：主机能确认尚未发出时，保存该编号的终止记录，阻止迟到请求执行；外部写入已经可能发出时，只返回“仍未知但结束本机等待”，不能撤销评论、PR 或推送。已确认的操作则返回原回执。本地提交可能同时影响分支与索引，必须先核实完整状态，不能直接关闭未确认记录。请勿手工删除数据库或未知锁文件来绕过保护。

本地提交还区分写入进程是否已收尾。主机在实际写入函数及其 Git 子进程结束后保存收尾证据；进程崩溃不会产生这项证据。只有已有证据、目录范围仍一致、会话空闲、分支与索引符合原基线且相关 Git 锁都不存在时，用户明确结束核查才会解除目录保护，保留未引用对象并永久禁止重跑原请求。单纯点击“核查”不会解除保护。分支与索引部分完成、存在锁或缺少收尾证据时，继续保持未知，需要在执行电脑处理；当前没有自动补写、删锁或强制释放入口。

## 数据和读取上限

token 仅在执行电脑的私有配置中保存。远端写入计划保存范围、请求摘要、恢复标记和结果身份，不保存 GitHub 读取正文或 token。**本地提交计划包含所选代码字节、提交说明、作者、时间及索引前后内容**，属于主机私有数据库备份范围，不能放入源码仓库或分发包。

浏览器持久保存手工草稿、明确复制的编辑内容、原待确认请求和最小回执；提交预览、PR 补丁与只读评论不进入 outbox。中转只转发请求和结果，不持久保存代码、评论正文、token 或写入回执。当前 HTTPS/WSS 没有额外端到端加密，中转进程可以看见转发中的用户发布内容。

REST 固定使用 `api.github.com`、API 版本 `2026-03-10`，不跟随重定向或正文链接；每次响应最多 2 MiB、10 秒。列表每页 20 项，手动翻页，最多第 100 页；补丁最多展示 65,536 字符，正文最多展示 16,000 字符，待发布正文最多 12,000 字符。部分页或截断内容始终不是全量结果。GitHub 的 PR files 接口本身最多返回 3,000 个文件，见[PR 文件接口](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)。Git 推送使用固定 GitHub smart HTTPS，另有 pack、响应字节与执行时间上限。
