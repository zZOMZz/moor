# 端到端加密延期与退场

独立加密工作区、v4 Host/Client、`secure` CLI、设备信任命令及专属构建资源已经退场。当前只维护统一工作区和 v3 连接，不继续补齐旧加密产品。历史实现与阶段计划可从 Git 历史查阅，不作为当前使用说明或验收证据。

## 当前传输边界

普通远程连接使用 HTTPS/WSS，TLS 在 Relay 终止，中转进程能够看到转发内容。Relay 不持久化会话正文，不等于端到端加密。凭据仍只属于私有配置；每个请求绑定账号、设备、工作区、项目与会话，只有原执行 Host 可以接受和持久化操作。

## 运行入口与已有数据

- Host 拒绝旧加密启动参数；CLI 拒绝 `secure` 和 `auth export-trust`，不会自动改用普通连接。
- Relay 拒绝旧 v4 和信任分发运行请求，当前构建不生成 `security.mjs`。
- 既有设备材料、恢复包、Host journal、浏览器记录和 CLI 原操作保留，不在升级或启动时删除、执行、封存或改投。
- CLI 用 `retired list` 和 `retired export` 离线读取原记录；浏览器仅提供旧数据只读检查和导出。未知结果继续保持未知。
- 普通草稿不在重连时执行；用户明确提交的新持久任务仍按独立授权与队列规则处理，不能由旧加密记录转换产生。

具体处置见[旧设备材料](device-security.md)、[CLI 离线归档](cli.md#退场数据的离线归档)和[浏览器升级](browser-client.md)。

## 验证要求

[退场回归](../tests/integration/retired-e2ee.test.ts)验证入口拒绝和旧记录保留，[浏览器旧记录回归](../tests/integration/retired-browser-records.test.ts)验证只读事务。`pnpm production:check` 检查构建产物不重新引入旧执行模块；当前普通工作区通过 `pnpm test:e2e` 验证。旧加密脚本的通过记录不能替代这些检查。

## 重新立项条件

先稳定统一客户端并完成核心设备验收，再根据明确威胁模型决定是否重新引入 E2EE。新设计需同时涵盖可信客户端、设备生命周期、密钥恢复、迁移和安全评审；作为连接属性复用现有工作区，不恢复第二套客户端，不静默降级到明文。
