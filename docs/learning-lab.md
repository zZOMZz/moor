# Moor 学习实验与自测

配套[系统学习指南](learning-guide.md)。本手册用仓库已有合成测试帮助你亲自检查关键行为，无需真实 Agent、Google 或 GitHub 账号。实验仅使用测试管理的临时数据，不要求接入自己的 Moor 数据库。

## 一、准备与实验方式

从仓库根目录执行命令，环境要求 Node.js 24+、Corepack 与锁定的 pnpm 10.20.0。依赖未安装时使用：

```sh
corepack pnpm install --frozen-lockfile
```

每个实验按“先预测、再读断言、运行、解释”的顺序进行。测试名是稳定的阅读线索，实际总数随项目开发变化，本手册不把某个测试数量作为长期承诺。

实验输出只留在自己的学习记录中，不把临时数据库、日志、真实会话或凭据加入仓库。以下命令运行现有测试，不需要修改产品配置。

## 二、六个核心实验

### 实验 1：主机确认到底确认了什么

对应指南第 5–6 章。

**先预测：** `delivered: true` 返回时，应该已经保存哪些数据？Agent 是否一定已经完成？同一原请求再次到达会发生什么？

阅读 [host.test.ts](../tests/integration/host.test.ts) 的 `fixture`、`request` 和测试 `delivery commits document, metadata and receipt atomically before Agent prompt`，再运行：

```sh
corepack pnpm exec tsx --test --test-name-pattern='delivery commits document' tests/host.test.ts
```

**观察点：** 回执 `delivered=true`；已保存历史包含用户与助手两个条目；Journal 中 phase 为 `accepted`；确定性 `started` 信号之后派发计数为 1；再提交相同请求，返回原结果且计数仍为 1。

**解释：** 送达确认主机持久接受。它不要求 Agent 已完成，更不证明输出正确。沿 [HostWorkspace](../packages/host/src/sessions/workspace.ts) 找到事务后的 `this.execute`，将测试断言与实现顺序对应起来。

**完成产出：** 自己画一条时间线，明确标出持久接受、开始执行、正常结束三个时刻。

### 实验 2：保存失败时是否可能偷偷执行

对应指南第 6–7 章。

**先预测：** 如果写会话快照失败，操作凭据会不会留下？模型调用是否可以先开始再补保存？

```sh
corepack pnpm exec tsx --test --test-name-pattern='failed persistence rolls back' tests/host.test.ts
```

测试在自己的合成 SQLite 上创建 `fail_snapshot` 触发器，让保存操作确定性失败。不要把触发器复制到真实主机数据库。

**观察点：** Mutation 被拒绝，Journal 没有该编号，会话元数据不存在，派发计数为 0。阅读 [RuntimeStore.transaction](../packages/host/src/persistence/store.ts) 的 `BEGIN IMMEDIATE/COMMIT/ROLLBACK` 和主机异常路径，解释数据库回滚与内存元数据恢复。

**解释：** 事务失败不能留下“收到送达凭据但没有会话”的局部结果，也不能派发 Agent。若把执行放在事务前，数据库失败时已经发生的文件修改无法由 SQLite 撤回。

**完成产出：** 用一句话说明为什么“先执行，之后尽力记日志”无法满足 Moor 的送达定义。

### 实验 3：两台设备同时发指令

对应指南第 4、7 章。

**先预测：** 两份基于同一历史的 CRDT 操作是否都应该运行？把相同 operationId 换一个项目重试是否允许？

```sh
corepack pnpm exec tsx --test --test-name-pattern='concurrent and offline turns|project and workspace scope' tests/host.test.ts
```

**观察点：** 两个新请求并发提交，只有一个被接受；断开后的新会话不派发；错误工作区或项目的操作被拒绝，已接受的操作也不能借重试跨范围访问。

**解释：** 文档可合并与操作可执行是两个判断。主机按会话串行，校验最近用户回合及活动状态。查询旧凭据不提供绕过身份与项目范围的通道。

继续看[目录测试](../tests/integration/catalog.test.ts)，找出同名项目与副本归组的行为；需要实际运行时使用：

```sh
corepack pnpm exec tsx --test tests/catalog.test.ts
```

**完成产出：** 画出账号、产品工作区、副本、执行工作区、会话，并在每个拒绝场景上圈出不匹配的范围。

### 实验 4：审批竞争和旧停止请求

对应指南第 8 章。

**先预测：** 手机选择允许，电脑选择拒绝，哪个结果会传给 Agent？主机重启后历史卡片还在，是否仍可批准？旧停止编号能否取消后来开始的回合？

```sh
corepack pnpm exec tsx --test --test-name-pattern='approval reaches only|cancel binds exact' tests/host.test.ts
```

**观察点：** 测试让合成 Agent 明确发出权限请求，再构造不同决定；第一份有效决定完成等待回调，后续新决定拒绝，原决定重试返回原凭据。错误助手回合的停止被拒绝，正确停止使等待审批取消。

**解释：** 审批需要持久历史与内存活动请求同时匹配。`expectedTurnId` 指用户回合，停止的 `turnId` 指助手回合，审批的 `requestId` 又是第三个维度。

**完成产出：** 写出 `session-s / user-u1 / assistant-a1 / permission-p1 / operation-op2` 各自的用途，并解释为什么不能只传 `session-s`。

### 实验 5：重启恢复历史，但不重放任务

对应指南第 7–9 章。

**先预测：** 主机已经保存送达凭据，但没有完成执行便退出。重开后重试原请求，派发计数应该是多少？手动发新回合又是多少？

```sh
corepack pnpm exec tsx --test --test-name-pattern='restart retains receipt' tests/host.test.ts
```

**观察点：** 测试只在自己的临时数据库中准备中断快照。新主机实例派发计数为 0；原请求重试返回旧回执，仍为 0；历史中的未完成回合已收束。手动发送新的合法回合后才出现一次派发。

**解释：** Journal 保留接受事实，不是开机消费队列。进程恢复、确认原操作、发送新回合是不同动作。原回合可能已经修改文件，所以用户继续前还要检查实际结果。

**完成产出：** 分别解释“接受后尚未派发就退出”与“文件已改但最终回复未保存就退出”。指出 Moor 能保证什么，不能恢复判断什么。

### 实验 6：真实协议，合成 Agent

对应指南第 3、8、14 章。

**先预测：** 不登录真实模型账号，仍能验证哪些 Agent 接入行为？加载原生上下文回放的历史会不会重复进入本轮输出？

```sh
corepack pnpm exec tsx --test tests/acp.test.ts tests/runtime.test.ts
```

阅读 [synthetic-agent.mjs](../scripts/validation/synthetic-agent.mjs)、[acp.test.ts](../tests/integration/acp.test.ts) 和 [runtime.test.ts](../tests/integration/runtime.test.ts)。后者使用真实 ACP driver，与合成 stdio Agent 跑两轮会话，中间关闭并重开主机存储。

**观察点：** 原生会话编号保留；审批只交给当前请求；历史长度随两轮输入增长；旧历史回放文本没有混进新回复；主机重开时没有活动执行。

**解释：** stdio、进程和 ACP 协议路径是真实的，模型与账号是合成的。因此能检验接线、生命周期和恢复，不能据此证明真实 Codex 登录、模型行为或 iPhone 体验。

**完成产出：** 给测试证据写一句准确说明，明确真实部分、合成部分与未覆盖部分。

### 一次运行核心实验集合

逐个理解后，可以一次跑覆盖这些实验的测试文件：

```sh
corepack pnpm exec tsx --test tests/host.test.ts tests/catalog.test.ts tests/acp.test.ts tests/runtime.test.ts
```

进一步的实际 HTTP/CLI 往返见 [cli-host.test.ts](../tests/integration/cli-host.test.ts)；显式加密链路见 [encrypted-cli-host.test.ts](../tests/integration/encrypted-cli-host.test.ts)。最终 bundle 与安装包专项的前置条件和命令见[开发文档](development.md)，不要把源码测试替代最终产物测试。

## 三、闭卷自测与参考答案

先遮住答案，尝试口述。答不出时回到指定章节，再从一个实现或测试中找依据。

### 产品与数据

**1. “本地优先”是否意味着完全离线、代码绝不经过网络？**

参考答案：它强调执行位置与数据所有权。本机模式不依赖中转，但模型可能需要网络；获授权客户端可以读取文件和 diff，Agent 可能向模型服务发送上下文。不能混淆保存、执行与传输。见指南第 2、5 章。

**2. 两台电脑的项目归到一起后，会自动同步代码和会话执行位置吗？**

参考答案：归组只改变逻辑组织和筛选。副本仍是各自主机的本地目录，会话继续绑定原执行位置；跨主机迁移是单独的后续能力。见第 4 章。

**3. 为什么已经保存 Moor 历史，继续会话仍可能失败？**

参考答案：Moor 历史与 Agent 原生上下文分开。主机私有保存映射，但 Agent 数据、登录、加载能力或固定运行环境失效时，不能仅靠 Moor 历史恢复原生上下文。见第 5、8 章。

**4. 主机、中转和浏览器分别备份能恢复什么？**

参考答案：主机保存 Moor 历史、身份与凭据等，但不构成完整代码或原生 Agent 备份；中转恢复账号、设备和组织关系；浏览器只有已读缓存及自己的草稿和原请求。见第 5 章。

### 执行与故障

**5. 已送达、助手 `handled`、检查完成分别说明什么？**

参考答案：已送达表示主机持久接受操作；`handled` 表示 Agent 调用正常返回；检查完成是用户处置结果的记录。都不能单独证明代码正确。见第 5–6、10 章。

**6. 用了 CRDT，为什么还拒绝并发发送？**

参考答案：CRDT 处理文档操作合并，执行需要符合活动回合和用户所见上下文。主机仍限制合法增量并检查 `expectedTurnId`；可合并不等于应该执行。见第 5、7 章。

**7. 手机发送后超时，为什么不能直接重新生成请求？**

参考答案：主机可能已接受。新编号代表新操作，不能证明与旧操作是同一次；必须保留完整原请求和编号进行手动确认。见第 7 章。

**8. “重试确认”会不会启动 Agent？**

参考答案：若原请求已接受，只返回原凭据；若从未到达且仍有效，这次手动重试可能首次接受并启动。不能把它当作纯读取。GitHub 的“核查原操作”则有不同的只读语义。见第 7、10 章。

**9. 主机先提交事务、后启动 Agent，这能保证外部副作用恰好一次吗？**

参考答案：不能。它保护 Moor 接受与去重边界，Agent、文件系统和外部 API 不在同一个事务中。文件已改但记录丢失时仍需核查实际状态。见第 6–7 章。

**10. 主机退出后自动恢复了，为什么原任务不自动继续？**

参考答案：恢复服务无法判断中断前已产生多少外部副作用。未完成回合被收束为中断，原凭据保留，后续执行需用户重新决定。见第 9 章。

**11. 为什么 `operationId`、`expectedTurnId` 和审批 `requestId` 不能合并？**

参考答案：分别标识业务操作、基于哪个用户回合继续、回应哪个活动权限请求。一个回合可能有多个工具请求，一次请求还可能经历多次传输。见第 7–8 章。

**12. 改了模型或本机 Agent 配置，原待确认请求会使用新值吗？**

参考答案：不能替换原请求的选项与身份。已接受重试返回原结果；新输入需按新能力明确发送。已有会话固定本机 Agent 配置版本，但该版本不等于二进制和账号的完整冻结。见第 6、8 章。

### 扩展与信任

**13. 旧回合的 diff 能证明当时全部文件都由 Agent 修改吗？**

参考答案：不能。主机基线保存受限扫描的前后差异，外部编辑可能进入其中，扫描也非原子文件系统快照；工具返回的 diff 另有来源和覆盖范围。见第 10 章。

**14. Fork 某个旧回合后，代码会回到旧回合的状态吗？**

参考答案：原生上下文截止与 Git 代码基线独立。原目录保留当前文件，独立 worktree 从明确提交创建，不复制未提交修改。见第 10 章。

**15. 工作台里的“需要继续”同步后，另一台设备有同一份后续草稿吗？**

参考答案：共享的是同账号处理状态，未发送草稿仍只在原访问端。带原事项引用的后续发送才由主机原子接受并记录关联。见第 10 章。

**16. 审查并启用任务计划，就启动子 Agent 了吗？**

参考答案：尚未。父指令手动发送并被接受后授权成立，父 Agent 再通过私有工具创建和发送子任务；创建目录或空会话也不等于执行。见第 10 章。

**17. 独立 worktree 和 MCP 逐回合授权提供完整 OS 沙箱吗？**

参考答案：worktree 隔离代码目录，MCP 授权限制 Moor 添加的连接与工具生命周期。Agent 原生权限和自身配置仍有独立边界，不应称为完整系统沙箱。见第 10–11 章。

**18. 中转不存正文又用了 HTTPS，为什么还要端到端加密？**

参考答案：不落盘不等于转发进程看不到；HTTPS/WSS 在中转处终止，默认 v3 的中转可见正文。显式 v4 在端点加密，仍需可信客户端和独立设备信任。见第 11 章。

**19. Google 登录成功，为什么不能直接接受中转给的设备公钥？**

参考答案：账号认证不证明公钥属于用户原先信任的设备。端点仍需验证用户核对的根与签名设备清单，不能据登录结果静默替换信任根。见第 11 章。

**20. 自动测试全通过，能宣称 iPhone 和正式安装包可交付吗？**

参考答案：只能说明所运行版本与用例覆盖范围通过。真机 Safari/PWA、系统生命周期、真实账号、签名公证和干净设备安装需要各自证据。见第 12、14 章。

## 四、设计推演

这些问题没有唯一实现答案。回答时先说明现有约束，再提出需要新增的机制，不把设想写成现有功能。

| 设想                           | 至少需要讨论的内容                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| 离线草稿恢复后自动执行         | 用户授权何时过期、旧上下文冲突、队列归属、重复消费与取消语义                                 |
| 将活动会话迁移到另一台 Mac     | 原生上下文能否迁移、代码与未提交文件、凭据、原主机停止证明、唯一执行所有权、未知操作如何交接 |
| 在中转保存完整历史以提高可用性 | 数据所有权与威胁模型变化、加密存储、删除/备份、密钥管理、与原主机事实的一致性                |
| 子任务自动判断目标完成并合并   | 完成条件的可验证证据、测试结果归属、冲突处理、精确提交、合并授权与失败核查                   |
| 新增一个远程文件编辑接口       | 项目范围、精确文件版本、审阅与接受边界、外部写入结果未知、旧客户端兼容                       |

推荐先选一个问题口述五分钟。能明确说出“现有设计提供什么、缺少什么、为什么不能直接复用某个状态”比提出很多新功能更能检验理解。
